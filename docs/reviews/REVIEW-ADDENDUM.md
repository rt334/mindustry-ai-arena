#### 实测装置与结果

**装置 1：矿机 8 邻格全放 `rot=0` 带子。**
矿机向所有邻格推货（无方向性），所以「哪条收到」只取决于带子自身的收货规则：

```
(270,87) 北排左   货从「南」来   收 ✓
(271,87) 北排右   货从「南」来   收 ✓
(269,88) 西侧上   货从「东」来   未收 ✗   ← 唯一拒收的方位
(269,89) 西侧下   货从「东」来   未收 ✗
(272,88) 东侧上   货从「西」来   收 ✓
(272,89) 东侧下   货从「西」来   收 ✓
(270,90) 南排左   货从「北」来   收 ✓
(271,90) 南排右   货从「北」来   收 ✓
```

**装置 2（定流向）：矿机南/东两侧各铺长链，看货堆在哪端。**

```
rot=0 链：M(270,88) → 272 273 274 275 276 277 278 279 全部铺满   ⇒ 向东流
rot=1 链：M(270,88) → (270,90..95) 全部铺满                       ⇒ 向南流
```

**⇒ `rot=0` = 东，`rot=1` = 南。** 与原文实测的 `0=东 1=南 2=西 3=北` **一致**。

#### 最终真值表

```
rot 编码   0=东  1=南  2=西  3=北
带子输出   朝向 rot 对应方向（货往下游推）
拒收       只有「正面」（= rot 方向 = 下游那一格）
收货       背面（rot 反方向，上游）+ 两侧
           背面条件宽松 minitem >= 0.4   ← 主收货口
           两侧条件更严 minitem >  0.7   ← 拐弯容易堵的真因
```

**代码算式对照**（`Conveyor.java:353`，`relativeTo` 编码 `0=西 1=北 2=东 3=南`）：

| 来源方位（rot=0，向东推） | `relativeTo` | `direction` | 结果 |
|---|---|---|---|
| 西（**背面/上游**） | 0 | 0 | 收，`minitem >= 0.4` |
| 北 / 南（**两侧**） | 1 / 3 | 1 / 3 | 收，`minitem > 0.7` |
| 东（**正面/下游**） | 2 | 2 | **拒收** |

**⇒ 四项全部与实机观测一致。**

#### 对原文的最终评价

**原文 `DEBUG-LOG §2.1` 的直觉是对的**：背面确实收料，而且这是主收货口。
**唯一不精确的是「只从背面」** —— 两侧也收，只是门槛更高（`> 0.7` vs `>= 0.4`）。

**而这恰好解释了原文那句「拐弯处不放 router 就必然静默堵死」**：
拐弯时货**只能从侧面进**，用的是严格条件，下游稍满一点就进不去。
**所以「拐弯要 router」这个工程结论完全正确，只是机理是「侧面门槛高」而不是「侧面不收」。**

### 定论实验（约 2 分钟，4 次对照）

固定一格带子，只改「货从哪个方位进来」，其余全不变：

1. 选一个空地带子 `T`，`rot=0` 放好，记录 `/buildings` 回读的 `rotation`。
2. 在 T 的**四个正交邻格**各放一个「已知出货」的钻机（独立测，一次只放一个，
   其余三个邻格留空——避免侧向误收）。
3. 每个方位单测：轮询 T 的 `items`，看多久出现货。
4. 判定：
   - **只有某一边进得来** ⇒ 那一边就是「正面」，据此定出 `rot → 方向` 映射。
   - **多边都进得来** ⇒ 就是「正面+侧面收、背面拒收」，原文的「只从背面」是误归因。
   - **都进不来** ⇒ 问题在别处（`minitem` 门槛 / 倒灌保护），不在方位。

**关键是要单侧隔离测试。** 原文的「两侧都铺带子看哪边先来货」同时开了两个方向，
会把「侧向也能收」误读成「只有一边收」。

**⇒ 对 A1 建议的影响（无论实验结果是哪个）：**
接口应该直接暴露**这张四元组真值表**（`方位 → 是否收 / 什么条件`），
而不是让 AI 去猜编码。现在的问题不是「规则是 A 还是 B」，
而是「**同一件事有两套方向编码在源码里并存，且没有任何接口暴露**」——
这才是 A1 真正的痛点，也是「图纸上对、实际堵死」的来源。

### 修正 A2 的一部分：钻机的 `rotation` 在我这版里有回读

原文说「`/buildings` 回读钻机的 `rotation` 恒为 0」。我这边实测有正常回读，
例如 `(309,99) mechanical-drill r0`、`(280,115) mechanical-drill r0`。
**可能是版本差异或特定情况下才恒 0。** 这一条建议先确认复现条件再改接口 ——
如果 rotation 本身是可信的，就不要从响应里删掉。

但原文的核心痛点成立：**实测 `rot=2` 对应两种不同输出格**
（`(68,101)→(67,102)` 西南、`(61,108)→(60,108)` 正西）。
这个现象的原因在 **footprint 锚点**：2×2 方块只有一条边是「正面」，
但锚点位置和接触边的关系不直观，所以同样的 rot 在不同位置看起来落点不同。
**⇒ 支持 A2 的建议：`/place` 返回里带上「实际生效的 rot + 输出格坐标」。**

## 二、原文没提到、但同样致命的四条

### 补 1. 混料：不同资源共用一条线会**互相顶死**，不是「减速」

**一条 conveyor 一次只持有一个物品**（`capacity = 3` 是长度计数，
但推进时一次一个）。所以两种资源共用一条线时，它们会互相卡住。

**我在这上面耗掉的时间最多。** 典型链条：

```
沙矿机把沙灌进本应运煤的干道
  -> 煤被沙顶住上不去
  -> 上游煤矿机满仓 eff=0.0
  -> 石墨压机没煤停机
  -> 没有石墨 -> 不能建 pneumati
c-drill -> 挖不了钛
```

**根因是一条容易被忽略的机制：矿机的输出不受 rotation 控制，
只要相邻格能接收就推。** 所以把一台沙钻机放在煤干道旁边，
它必然往干道里灌沙 —— **这不是「铺错了」，是「放在别人的物流线旁边」这个动作错了。**

**⇒ 建议新增接口需求：`/buildings` 里每台钻机给出「它实际在往哪几格推货」**
（同理 A2 想要的东西，但对钻机尤其重要）。
或者更直接：**矿机的 footprint 邻格里，哪些属于别的资源的干线，给出告警。**

### 补 2. 下游满仓会**反向堵塞整条上游线**

**核心铜满（达到 13000 上限）→ 铜线全堵 → 上游铜钻机全部 `eff=0.0` 且满仓。**
这不是「铜线有问题」，是**核心吃饱了**。

**判据（很实用）：`eff == 0.0` 且 `items` 达到容量上限 = 输出路径不通。**
不是「没矿可挖」，是「挖出来运不走」。

**⇒ 建议**：`/stalls` 或 `/diag` 里区分「上游来货不足」和「下游拒收」两种停机。

### 补 3. 队列卡死时，一条移动命令能解开（不用拆方块）

现象：`plans` 长时间不变、建筑数不变、建造单位位置不变（**要连续采样确认，
单次读数不变可能是正常消化**）。常规手段无效：

- `break` 幽灵格**有效**，但只能清 `build*` 那几种
- `break` **空格**想取消排队中的计划是**无效的**，反而**追加**拆除计划
  （实测 `plans` 47 → 56）

有效手段：

```bash
POST /control?op=order&unit=<id>&x=<格>&y=<格>
```

**实测 `plans` 一次从 56 降到 1**，而且沿线的方块真的建成了。
单位卡在某个建造状态里，移动命令重置了它的状态机。

**⇒ 建议**：A4/A5 之外，`/queue` 应该能判断「停滞」并提示这是个可操作项。
另外 `/control?op=order` 的坐标是**格坐标**，不是像素 —— 这一点也值得写进文档。

### 补 4. 建造受视野限制，返回的是 **HTTP 403**

`/place` 对视野外的格子返回 `HTTP Error 403: Forbidden`（**不是** `ok:false` 的 JSON 体）。
错误处理只看 JSON body 会误判。视野半径约 61 格。

**⇒ 这构成一个鸡生蛋**：要建远处需要那里的视野，要有视野需要先有建筑。
突破口是**视野来自己方建筑，所以铺干线本身就在推视野** ⇒ 远距离扩张必须分段推进。

**⇒ 建议**：`/content` 或 `/state` 暴露视野半径；403 响应体里写明原因。

## 三、对 C 节（公平性红线）的看法

同意原文的划分标准：

- **暴露「规则」不算降低难度**（每格 `acceptsFrom/sendsTo`、钻机实际输出格）

等于开局前就知道煤/钛分布。这与「公平竞技」有张力，建议在文档或权限层明确。

## 六、对 REPORT.md / DEBUG-LOG.md 的核对

### 6.1 矿机产出：精确公式（可用来核所有速率数字）

源码链条：`Drill.java:305` 的 `progress += delta() * dominantItems * speed * warmup`，
当 `progress >= delay` 时产出一个物品，`delay = getDrillTime(dominantItem)`。

**⇒ 速率 = `dominantItems × speed / getDrillTime(item) × 60`（物品/秒）**

其中 `dominantItems` = footprint 覆盖的**矿格数**（`Drill.java:277`），
`getDrillTime = (drillTime + 50 × 硬度) / drillMultipliers`。

煤 hardness = 2（`Items.java`），所以附加 100 帧。**本图无水，`speed = 1`：**

| 矿机 | drillTime | 覆盖 | 每台 | **每矿格** |
|---|---|---|---|---|
| `mechanical-drill` | 600 | 4 | 0.37/s | **0.092** |
| `pneumatic-drill` | 400 | 4 | 0.48/s | **0.120** |
| `laser-drill` | 280 | 9 | 1.42/s | **0.158** |

**注意 `覆盖格数` 会在「矿格数 × 每格产能」里自动抵消**：
总产能 = (矿格数 / 每台覆盖) × (每台覆盖 × 每格) = 矿格数 × 每格。
所以用「矿格数 × 每格」估总量是**对的**，前提是每格那个数取对。

### 6.3 「5/s 不可达」这个结论：适用范围不同，两边其实不矛盾

| | 对方的算法 | 我的算法 |
|---|---|---|
| 范围 | **近处**有效煤格 ~50（扣除被占的 26 格） | **全图** 1112 煤格 |
| 上限 | 约 7.5 ~ 10.7 煤/s | 56 台 laser 不重叠 ⇒ 79.5/s |
| 需求 | 16 煤/s（石墨 10 + 硅 6） | 同 |
| 结论 | **不可达** | **可达** |

**两者不冲突，是范围不同，而这恰好指明了真正的约束在哪：**

- **「近处」这个前提是对的、也是务实的。** 我第 21 轮算出全图 79.5/s 后就宣称可达，
  但第 26 轮才发现**把远处的煤接回来需要 60+ 格的干线**，而那条路上有：
  视野半径 61 格（超了直接 HTTP 403）、只有**一个**建造单位、队列积压。
  **⇒ 我算的是地质上限，对方算的是工程上限。工程上限才是约束。**
- **两者合起来才是完整答案**：短期（近处）确实不可达；
  长期（全图）在数学上可达，但代价是巨量基建，而且在「单建造单位 + 视野限制」下
  是否现实，我没有验证过。

**⇒ 建议 REPORT.md 的结论保留，但把「原因是矿量」改成
「原因是**近处**矿量 + 干线成本」** —— 前者是地质事实，后者是工程事实，
而决策受后者支配。

**移动命令可解开停滞队列**、**视野 61 格导致远距离建造返回 HTTP 403**。

### 6.6 一条工具层面的补充

对方的 `acc4.py`（按自维护清单循环 warp 建造单位）解决的是
「一个 builder → 一堆待建方块」的吞吐问题，实测 400 次 warp 清掉 59 项。

**我这边的对应手段更轻、但依赖一个未文档化的行为**：
队列停滞时用 `POST /control?op=order&unit=<id>&x=&y=` 把单位送到工地，
实测 `plans` 一次从 56 降到 1，且沿线方块真的建成。
**区别在于：对方维护了一份 pending 清单来主动驱动，我是被动等它停滞再去解。**
前者更稳（不依赖「停滞」这个条件），但需要自己维护状态；
后者更省事，但只在卡住时生效。

**⇒ 如果 B3（多建造单位）/ B2（builder 可观测性）做了，这两种 workaround 都可以退役。**
