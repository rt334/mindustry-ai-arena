# ai-arena 实战调试复盘

一次单人单队的完整产线攻坚（7 轮）。本文只记录**途中遇到的问题、定位手段、解决方式**，以及最终沉淀下来的做法。产线本身的结论见 `REPORT.md`，接口层的改进建议见 `FEATURE-REQUESTS.md`。

---

## 1. 起步就撞上的两个前提问题

### 1.1 有另一个进程在操控同一支队

**现象**：我按图纸建的布局里冒出了我没建的方块——`(64,107)` 的熔炉、`(65,100)`/`(66,100)` 一带的带子。我的建造计划频繁「成功但不生效」。

**定位**：查 `Get-CimInstance Win32_Process`，发现 `ai-client.py --agent alpha --token <alpha>`（PID 44384）在跑，日志显示它正在往煤线里插带子、和我抢同一批格子。

**解决**：停掉它（`Stop-Process -Id 44384 -Force`），保留 beta / agent3 / agent4 作为对手。之后每一次改动的效果才可归因。

### 1.2 建造请求排队，但「成功」不代表生效

**现象**：`/place` 返回 `{"message": "queued ... pending plans=1"}`，方块却迟迟不出现。早期我按「下单 → 等它建好」的思路写脚本，拿到一堆假结论。

**解决**：立一条纪律——**判据必须是状态，不是时长**。所有确认改走轮询 + 命中即退（`poll_until(pred, timeout)`），代码里不出现裸 `sleep(N)`；采样间隔 `sleep(0.1)` 允许，因为它每次醒来都检查状态。

## 2. 最大的时间黑洞：接口语义全靠实验反推

技能文档刻意不写游戏内情，所以下面每条都是用**对照实验**测出来的，不是读来的。

### 2.1 传送带只从背面收料 ★

**现象**：链在设计上「每格都朝下一格」，实际全堵。`/place` 成功、`/buildings` 显示带子在、`rotation` 也对，物品就是不动。

**定位**：把 `/stalls` 里所有 `inputSide` / `outputSide` 字段与坐标交叉比对，发现带子只接受来自**背面那一格**的物品。拐弯处不放 router 就必然静默堵死。

**代价**：整版布局推倒重来两次。后面自建 `outlet_audit.py` 逐台钻机算四个输出侧谁在接货，才把这类问题从「玄学」变成「可查」。

### 2.2 rot 的真实语义

**定位**：从旧布局里一条已知正确的链反推——`(60,108)` 从东侧钻机收货且朝西输送 → `rot=2` 是西；再用 `(58,107)`、`(64,101)` 交叉验证，得出 `0=东 1=南 2=西 3=北`。

### 2.3 钻机往哪边推货

**定位**：在钻机两侧都铺带子、末端留空，看哪条先拿到 items。测出三组：

| 钻机 | rot | 实际输出格 |
|---|---|---|
| (68,101) | 2 | (67,102) —— 西南格 |
| (61,108) | 2 | (60,108) —— 正西格 |
| (66,114) | 3 | (66,113) —— 正北格 |

**关键发现**：同样 `rot=2`，输出格的相对位置还不一致，所以无法推导，只能逐台实测。另外 `/buildings` 回读钻机的 `rotation` **恒为 0**，完全不能当判据。

### 2.4 电力必须用 power-node 连线

**实验**：发电机与熔炉隔一格 → `powerStatus` 一直是 0；中间补一个 power-node → 立刻变 1。相邻不会自动并网。

### 2.5 核心不向下游倒货

**实验**：在核心南缘 `(63,107)` 挂一条朝外的带子，轮询 40 秒，items 一直为空。

**含义**：核心里积压的煤**无法回收**——这解释了早期「煤全进了核心、压机却饿死」这一现象。

## 3. 三类跑不出数据的硬故障

### 3.1 僵尸计划挡住出口

**现象**：`(68,100)` 长期停在 `build3` 状态，占死 2x2 footprint，把 `(71,98)` 铜钻机的唯一出口堵了两轮。

**定位**：拿 `/map` 的 `build` 字段和 `/buildings` 对照——`/map` 说那里有方块，`/buildings` 里它永远不变成正式方块。

**解决**：`break` 掉它，腾出 `(69,99)`~`(69,101)` 的通道。

**效果**：铜 **1.86 → 2.26/s**。

### 3.2 混料导致整条煤道死锁

**现象**：硅长期为 0。`/stalls` 报熔炉缺煤，但更上游的带子上明明有煤。

**定位**：`trace.py` 逐格打印 items，看到 `(65,112)` 上卡着一颗石墨——压机把石墨倒回了煤道，石墨随煤流到熔炉，熔炉不收，整条线静止。

**解决**：在 `(65,112)` 装 `sorter`，`/config` 设 `value=coal`：煤送前方熔炉，石墨从侧面被带走。（注意 `place` 的 `config` 参数无效，必须后置调 `/config`。）

**效果**：硅 **0 → 0.35/s**。

### 3.3 断带被别的方块压住

**现象**：钛长期 0，钛钻机 `drillBlocked`。

**定位**：`tibelt.py` 打印 y=106 整行，发现 `(55,106)` 的 `rotation` 是 1（朝南）——早先的煤改道链把这格压成了南向带子，整条钛带被截成两截，钛在带上堆到 3/格却过不去。

**解决**：把那格改回 `rot=0`。

**效果**：钛 **0 → 0.65/s**。

### 3.4 死口钻机（同类问题的批量形态）

`(67,80)` 的 2x2 钻机东侧和南侧都是邻居钻机，货永远推不出去；`(52,83)`、`(39,100)`、`(71,98)` 都是同一类。解法是把它「正对输出侧」的那两格腾出来（拆邻居、或补带子）。

## 4. 优化掉的东西

| 优化项 | 做法 | 效果 |
|---|---|---|
| 建造吞吐 | 单位 `buildSpeed=1.0`，时间几乎全花在走路上。写 warp 加速器：按自维护的待建清单轮询并持续把单位送到下一个待建点 | 400 次 warp 清掉 59 项待建 |
| 物流架构 | router 只用在拐弯处，直线段一律带子（14 个 router 串联那条链吞吐直接崩了） | 消除一类静默堵塞 |
| 工厂布置 | 工厂优先贴着核心建，产物被核心直接吸走，省掉出料带 + 汇流带两层 | 减少中间环节，少一处会堵的地方 |
| 电力结构 | 烧煤发电机每 1 电吃 0.5 煤/s，和压机抢煤。改用 23 块太阳能板（铅 10 + 硅 8，不烧煤） | 煤全部让给石墨生产 |
| 钻机升级 | 用压机产出的石墨把机械钻换成 pneumatic-drill（每格 0.092 → 0.133；煤因硬度 2 是 0.086 → 0.120。不吃电） | 铜/铅/煤同步 +40~44% |
| 混料分离 | 工厂产物混进燃料线 → 用 `sorter` / `inverted-sorter` 按物品分流 | 解掉两处死锁 |
| 诊断链 | `outlet_audit.py`（逐台钻机算四个输出侧谁在接货）→ `trace.py`（逐格 items）→ 修 1~2 格 → 复测 | 从「读两百条 JSON」变成定点手术 |

## 5. 沉淀下来的方法论

1. **判据是状态，不是时长**。任何「等它建好」都必须轮询到状态出现；`sleep` 只能作为采样间隔。
2. **先测量再下结论**。速率、朝向、连接规则全部实测；`/content` 只给方块元数据（cost/size/hp），配方和速率得自己测或从行为反推。
3. **对照实验优于读文档**。接口语义不明时，构造最小对照（两侧都铺、看哪边先来货），30 秒就能定性。
4. **改动必须可归因**。一次只改 1~2 格，改完立刻复测；否则无法判断是改动生效还是别的因素在动。
5. **先清场再重建**。旧布局的残留（错向带子、僵尸计划）会持续制造假信号，清干净比打补丁快。

## 6. 结果与未解决的部分

**五项目标的起点 → 终点**：

| 资源 | 起点 | 终点 | 倍数 |
|---|---|---|---|
| 铜 | +1.24/s | +2.26/s | ×1.82 |
| 铅 | +0.77/s | +1.61/s | ×2.09 |
| 石墨 | 0 | +0.75/s | 从零 |
| 硅 | 0 | +0.35/s | 从零 |
| 钛 | +0.03/s | +0.65/s | ×21.7 |

**没解决的是矿量本身**（已量化，见 `REPORT.md`）：近处有效煤格约 50 格，上限 6.0 煤/s（全换激光钻也只 7.9），而「石墨 5/s + 硅 5/s」合计需要 16 煤/s；钛近处只有 10 格可用，旁边 28 格整片被 shale-wall 封死；东北那个 49 格大煤簇经逐格 `/map` 验证是被 spore-pine/shale-wall 包围的飞地，进不去。
