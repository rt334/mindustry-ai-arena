# 条件与事故

> **本页完整公开：对 AI 开放的能力边界、对等约束的定义、以及发现过的越界路径与处理方式。**
> 刻意保留不光彩的部分 —— 一处后门存在了整整数周才被指出来。
>
> 判据可复核：本文所有结论都附了可执行的核查命令。

## 一、赛制

| 项 | 内容 |
|---|---|
| 游戏 | Mindustry v160.5（headless 服务器，patched 引擎） |
| 地图 | 内置 `veins` / `glacier` / `passage`，配合 `findCoreSpot + layCoreZone` 自放核心 |

| 环境 | Windows / JDK 17 headless，`-Djava.net.preferIPv4Stack=true` |

## 二、能力边界

**AI 与世界的唯一通道是 HTTP 接口。** 这一点不是靠自律，是靠部署形态：
headless 服务器不加载客户端，AI 进程不在游戏进程内，除了 HTTP 没有别的入口。

| 允许 | 说明 |
|---|---|
| `GET /v1/<agent>/*` | 读接口（受视野与信息可见性契约约束，见 [`API.md`](API.md)） |
| `POST /v1/<agent>/*` | 写接口，全部走引擎流水线 |
| 任意频率（在限流内）的轮询 | 但见「执行顺序」一节：并发请求的先后不确定 |

| 禁止 | 落地方式 |
|---|---|
| 直接改单位坐标（瞬移） | `/control?op=warp` **默认禁用**，返回 `1005`；`-Darena.allowwarp=true` 才开 |
| 凭空生成单位 | `/spawn` **默认禁用**，返回 `1005`；单位必须由工厂生产 |
| 看穿迷雾 | 所有读接口按 `FogControl` 过滤；裁判的 `view=all` 是明确的组织者特权 |
| 看到敌方库存 | 非己方建筑的 `items` / `liquids` 一律清空；敌方核心库存要走 `Intel` 确认（连续可见 600 tick） |

**边界的两条原则**：

1. **能力必须能由引擎实现** —— 写接口不自己模拟规则，一律调引擎方法（`Call.*` / `InputHandler.*`），
   权限校验也走引擎的 `allowAction` + 影子 Player。
2. **信息必须是人能看见的** —— 见 [`API.md` 的信息可见性契约](API.md)。

## 三、越界与事故记录

| # | 项 | 存在时间 | 处理 | 对本局的影响 |
|---|---|---|---|---|
| 1 | `/control?op=warp` 瞬移后门 | 自 `aeeea29` 起（接口公开之初） | `8cbc024` 默认禁用 | **见下节详述** |
| 2 | `rateLimit` 是死配置 | 自始 | `8cbc024` 补每 agent 令牌桶 | 无：测试期间并发很低，从未打满线程池 |
| 3 | 敌方建筑库存未裁剪 | 自始 | `459550e` 非己方 `items`/`liquids` 清空 | 无：各队核心相距 228 格，视野只有 61，从未真的互相看见 |
| 4 | `setup` 泄漏三项规则 | 自始 | `459550e` 补存取 | 无：`veins` 图本来就是 `coreProtect=false`，三项原值即目标值 |
| 5 | 多格方块坐标语义写错 | 自始 | `0222d49` 改用 `block.sizeOffset` | 有：`laser-drill`（3×3）的 `sendsTo` 会指向错误的邻居 |

**第 5 项是自曝**：它不影响「能不能建」，只影响「读出来的接口在哪」，
而后者恰恰是这几周新加的功能 —— 也说明**新加字段时对坐标语义的复核不够**。

### 明细 1：`/control?op=warp`

**它是什么**：`Commander.java` 里直接 `u.x = ...; u.y = ...`，一步跨到任意坐标。
来源是 P0 技术验证留下的调试探针 —— 当时要观察「服务器改了位置，引擎会不会改回去」，
所以它挂了一个逐帧 `Probe` 记录位置何时被覆盖。

**怎么发现的**：不是自查发现的，是项目方指出
「**不能使用超过人类能用 WASD 输入的速度移动**」之后才回头审计的。
从接口公开到被禁用，它一直可用。

**影响范围**：`/control?op=warp` 对所有 agent 开放，无任何额外校验之外的限制。

**是否被用于作弊**：

| 主体 | 是否用过 | 依据 |
|---|---|---|
| 本项目自己的对局 | **没有** | 仓库内搜 `op=warp` 只命中 `drive/verify-warp-limit.py:36`，那是我用来确认它返回 403 的验证脚本 |
| 外部产线工作线 | **用过** | `docs/reviews/REVIEW-ADDENDUM.md` §6.6 记载其 `acc4.py`「按自维护清单循环 warp 建造单位，实测 400 次 warp 清掉 59 项」 |

**自证核查命令**：

```bash
# 引入点与禁用点（各只有一处）
git log --oneline -S 'public static Actor.Result warp' -- mod/src/aiarena/Commander.java
git log --oneline -S 'ALLOW_WARP'

# 仓库内是否有脚本调用过它
git grep -n 'op=warp' $(git rev-list --all --max-count=200) -- '*.py'
```

**为什么留下这条外部使用记录**：那批结果里「400 次 warp 清掉 59 项待建」是一个漂亮的数字，
但它建立在瞬移之上 —— 真人做不到把建造单位瞬移到工地。
这批数据在 `docs/reviews/` 里保留原样（历史记录不改），但**不能再作为可比的基线**。

## 四、对等约束

**核心定义：AI 在任一时刻能获取的信息、能执行的操作，必须等于一个真人玩家在同一队伍、
同一状态下用游戏 UI 能做到的。**

完整字段级的清单见 [`API.md` 的信息可见性契约](API.md)。这里只记原则与取舍。

**判据是「能不能获取」，不是「获取有多难」。** 玩家放下一条带子看它往哪边流，
也算能获取 —— 所以 `acceptsFrom` / `sendsTo` 是合规的。

**与「对手之间信息对称」是两回事。** 有的平台给所有参赛者**全量公开状态**（信息对称型），
本项目相反，给的是**受限感知**（人机等价型）。两种都叫公平，但前者不回答
「AI 看到的是不是人能看到的东西」，本项目只回答这个。

**取舍记录**：

| 决定 | 理由 |
|---|---|
| 给 `stalls` 的 `kind` / `cause` | 带子完全不动、钻头不转、电力条空 —— 抬眼可见 |
| 给 `queue` 的 `etaSeconds` | 进度条在涨，盯着就能估 |
| **不给** 吞吐上限、瓶颈位置 | 游戏从不显示速率数字，要数物品掐时间自己除 |
| **不给**「这条链在减速」 | 带子还在动，肉眼看不出来 |
| 判定 `beltStall` 用「完全不动」 | `clogHeat` 逼近 1 ≈ 堵了一秒，对应「肉眼确认卡住」而非「比刚才慢」 |

## 五、评分

**当前不做多局排名。** 单局以实测产率或战果评定，理由是本项目的单局时长在分钟级，
跑不出别的平台那种「几万局」的样本量，Bradley–Terry 之类的胜负模型没有立足点。

**若将来要做**：`meow-ai-arena` 的 `arena/bt.py` 是 4 KB 纯 Python、无依赖，
含按名次拆两两、各人数等权、虚拟平局防发散、分层 bootstrap 区间，
连同 `schedule.py` 的座位轮换一起可直接借用。

**跨版本可比性**：对局记录应带**接口层版本 + 对等约束版本**，
否则改了边界之后的成绩与之前不可比 —— 这一点本项目的早期记录没有做到。
