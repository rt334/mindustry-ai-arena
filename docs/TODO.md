## 二、功能缺口

### 2.1 回放 ✅ 已完成

**[`replay/index.html`](../replay/index.html) —— 单文件零依赖，拖入 `.jsonl` 即播。**

骨架借鉴 meow-ai-arena 的 `viewer.html`（8.3 KB 纯前端 + canvas，
证明「回放不需要重放引擎，只要状态序列 + 一个画法」）。三处必须不同：

| | 它 | 我们 |
|---|---|---|
| 数据载入 | 录像几百 KB–2 MB，`const R=/*__REPLAY__*/null` 内嵌进 HTML | 几十 MB，**不能内嵌** → `<input type=file>` + `file.stream()` 逐块读 |
| 跳转 | 帧是全量，seek 是 O(1)，敢不做索引 | `builds` 是**增量**，必须重放 → **每 100 帧存一份建筑副本**，把 O(n) 降到 O(100) |
| 地图 | 明文数组内嵌在 header | 三段 **RLE**（floors/ores/walls），客户端解码 |

功能：播放/逐帧/进度条/1–10× 倍速、跳到关键事件、点队伍高亮过滤、网格、1–8× 缩放。
地图按名称哈希配色（不需要知道是哪张图），建筑画队伍色块 + 朝向三角 + 首字母。

**这次动手前先做了「数据够不够画」的验证，结论是不够，补了四样**（见 git `c51ecb5`）：
地图（完全没有）、建筑 `rot`、被拆方块的记录（`removed`）、`items`（可选，未做）。
其中 `removed` 那条最隐蔽——`knownBuilds` 每帧用当前全量替换，拆掉的方块从集合
消失后**不写任何记录**，回放端会一直画着它。

**验证方式**：没有 headless 浏览器，但「重建出来的状态对不对」是纯逻辑。
`drive/verify-player.js` 把播放器里那几段函数抄出来跑真实录像，用两套互不相干的
算法对账（Map 覆盖+删除 vs 集合差），并抽查 checkpoint 重建与从头重放是否等价。
实测一份专门造来覆盖全分支的录像（建 5 条带子、拆 2 条、再建 2 条）：
出现过 11 个 key、被拆 2 个 → 最终 9 个建筑，两套算法一致。

**仍未做**：`builds[].items`（能看出谁堵了，画面信息量更大）、sprites 渲染
（现在是最简的色块+字母档）、长时间录像的滚动加载（目前全量解析进内存）。

### 3.5 验证手段本身的结构问题

**所有验证都要起服务器或起游戏** —— 这才是债务会累积的根因：成本高，于是「下次再验」，
于是清单越来越长。可离线断言的部分其实不少，它们**不需要游戏**：

### 7.5 教训（写给后来人）

| # | 教训 |
|---|---|
| 20 | **调试前先确认没有别的进程在操控同一支队**。`ai-client.py --agent alpha`（PID 44384）在后台往同一批格子插带子，导致「建造计划成功但不生效」，在此之前所有改动都不可归因。查 `Win32_Process` 是第一步。 |
| 21 | **「排队成功」不等于「生效」；判据必须是状态，不是时长**。`{"message": "queued ... pending plans=1"}` 之后方块可能永不出现。纪律是全部走 `poll_until(pred, timeout)`，代码里不出现裸 `sleep(N)`。 |
| 22 | **混料是「互相顶死」不是「减速」**。一条 conveyor 一次只持有一个物品（`capacity=3` 是长度计数），两种资源共用一条线会互相卡住。典型链条：沙灌进煤干道 → 煤上不去 → 上游煤矿机满仓 `eff=0.0` → 压机没煤 → 没石墨就建不了 pneumatic-drill → 挖不了钛。**根因不是「铺错了」，而是「把它放在别人的物流线旁边」这个动作错了。** |
| 23 | **静态分析在方向语义上不可靠，必须单侧隔离实测**。用「两侧都铺带子看哪边先来货」会把「侧向也能收」误读成「只有一边收」；正确装置是**一次只开一个方位**，或用「矿机 + 8 邻格全铺同 rot 带子」让被测格只暴露收货规则。 |
| 24 | **旧布局残留会持续制造假信号，先清场再重建**。错向带子、僵尸计划（卡在 build 状态占死 2x2 footprint、堵掉钻机唯一出口、损失约 0.4/s）都是「一次只改 1~2 格 + 立刻复测」之后才定位的；打补丁不如清干净。 |

### 10.1 诊断：三个症状是一个根因

| 症状 | 诊断 |

| 思考慢 | LLM 秒级 vs 引擎 60 tick/s，差两三个数量级，**这一层无法消除**。但它不该是主要矛盾 —— 引擎本来就自主运转（[ENGINE-NOTES](ENGINE-NOTES.md) §三十二：单位自主交战、矿机自采、传送带自运），AI 不在场的 tick 世界照样转 |

| 迭代慢 | 上面两条的后果。**而且轮询不是免费的** —— 每次轮询都是一趟 LLM 往返，等一次建造可能烧掉几十轮模型调用 |

### 10.4 约束（做 `/await` 时必须守）

**它只允许等该 agent 本来就能看到的信息**（自己队的 `rate` / `stall` / `queue` / 建筑），
**不接受跨队谓词** —— 否则就变成「用服务端算力换情报」，越过对等约束。
做法参照 `/watch`：只聚合自己队的。

**2026-10-06 发现**：`/database` 曾经读入 `block=` 与 `type=` 两个参数，

**第一次自测就红了**，抓到的是样本本身的问题（变量名与 key 同名，key 字符串里的同名被算成"用过一次"）。

## 十二、原始目标（各 +5/s）的可行性 —— 全图矿脉实测

**2026-10-06**：第四轮对照测试里，agent 用 `/drill` 的 `itemsPerSecond` 外推，得出
「石墨 5/s 需约 27 台煤钻机，而本图煤矿簇只能容纳约 4 台 ⇒ 用机械钻机**物理不可达**」。

**这个结论是错的。** 它只看了自己选中那一片煤矿簇 —— 而 `/map` 分片扫全图（70000 格）后：

| 矿种 | 全图格数 | ÷4（一台 2×2 钻机吃 4 格） | 5/s 需要 |
|---|---|---|---|
| sand | 26788 | ~6697 台 | — |
| copper | 2338 | **~584 台** | 约 14 台 |
| lead | 1098 | ~274 台 | 约 14 台 |
| **coal** | **642** | **~160 台** | 约 27 台 |
| titanium | 474 | ~118 台 | — |
| thorium | 244 | ~61 台 | — |

**所以各 +5/s 是可达的。** 约束**不是矿量**，而是「**把散布全图的远矿接回来**」——
物流干线的长度、以及 15 分钟里能完成多少回合，才是真瓶颈。

**教训：别拿局部采样推全局上限。** 那个 agent 的算术没错（27 台 > 4 台），
错在把「我脚下这片只能放 4 台」当成了「全图只能放 4 台」。
**而我把它的结论原样转述成了「物理不可达」——同一个错误的第二次传播。**
`/map` 扫一遍全图只要 24 次请求（一次上限 4096 格）。

（同格换气动钻机是 1.41× 这条仍成立：实测机械 0.34/s → 气动 0.48/s，成本 18 铜 + 10 石墨。）

### 要不要把这条告诉参赛 AI

**不说结论**（「5/s 不可达」是推导，属于结论 —— 见 [§7.9](#79-补进-六-的边界判定) 的边界），
**但值得让他们知道「目标可能受地图支配」**，否则他们会把整个回合烧在堆设备上，而堆不出来。
已按这个口径写进 [PROMPTS.md](PROMPTS.md) §二：

> 如果发现某条线即使铺满也上不去，先判断挡住它的是**设备数量**还是**矿脉本身**，
> 把结论报出来比硬堆更有用。

| # | 问题 | 实测证据 |

### 13.5 接口缺陷放大它们（已修的归因，不是 AI 的错）

列出来是因为**不列就会把账算在 AI 头上**。

| 缺陷 | 后果 | 状态 |
|---|---|---|
| `/stalls` 返回**全图所有队伍** | 它一次拿到 40 条，**39 条是对手的**；自己那条缺煤报警只是 1/40。它读了 25 次告警，没有一次朝自己那条 15 格的煤线去 | 已修 `51d6dac`（按 `view` 裁剪，判据与 `/buildings` 逐字一致） |
| `/block` 的 `outputs` 不覆盖泵类 | `water-extractor` 的 `outputs` 是 `[]` —— 它对 AI 的回答是「**这个方块什么都不产**」 | 已修 `d0c7ce9`（补 `SolidPump` / `Pump` 分支 + `baseEfficiency` / `attribute`） |
| `/database?item=` 不认液体 | `?item=water` 返回 **404 `unknown item`** —— 而「谁产它」本是这个端点存在的理由 | 已修 `125fc8a`（液体走独立分支，`producers[]` 的 `how` 区分 crafter / solid-pump / pump） |
| **转运件在 `/block` 里是空数组** | `junction` / `router` / `sorter` / `overflow-gate` / `underflow-gate` / 各类桥与卸载器的 `inputs` 与 `outputs` **都是 `[]`** —— 而「怎么送」是它们唯一的语义。AI 据此认定这一类「什么都不做」，整局没建过任何分流件：223 条传送带的 `sendsTo` 长度全为 1，7 台钻机配 177 条带 ≈ 7 条「钻机直线回核心」，「一路料分给八台设备」在它那边**没有名字** | 已修 `fe667e8`（`outputs` 加 `kind=transport` + `how` + `note`，覆盖 39 个方块；`how` 用引擎 `invert` 区分 `sorter`/`inverted-sorter`、`overflow-gate`/`underflow-gate`） |
| `AUTO_SPECTATE` 默认 `true` | 真人一连入就被移出队伍、清掉单位 —— 那一局靠 `-Darena.autospectate=false` 才进得去 | 已修：默认保持 `true`（观战端 mod 靠服务端标 spectator），改由 `-Darena.players=<名字>` 白名单回答「谁该当玩家」 |
| **菜单状态下接口「坏了一半」** | `postToGame` 的每 tick 写预算按 `Vars.state.tick` 重置，而菜单状态 tick **恒为 0** ⇒ 预算用尽一次后，**所有走主线程的端点永久回 1007（HTTP 504）**，不走主线程的 `/ping`、`/state` 却正常。实测连打 40 次 `/diag` 即触发，报的还是「game thread did not respond」这种误导说法 | 已修 `fe667e8`（没在游戏中就不做预算限制）；修后 40 次全部 200 |

**这一整批伤在同一句话上**：`找不到` 和 `不存在` 在接口上返回同一个东西，
所以 AI 无法区分。**它的推理没有错，是接口答了「没有」** ——
而它每次都去问了：水（三处）、矿脉、转运件。
