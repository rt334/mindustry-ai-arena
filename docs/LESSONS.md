# 经验教训

这份是从一次长会话（30 轮）里沉淀下来的。**只写踩过的、有具体出处的坑**，
不写「要注意代码质量」这类正确但没用的话。

每一条都带一个真实例子 —— 没有例子的教训，下次还是踩。

---

## 一、判定与核实

### 1.1 命中 0 能证伪，命中 ≥1 不能证真

用 `grep` 数命中次数来判断「某个功能实现了没有」**只能得出否定结论**。

真实例子：我数到 `acceptsFrom` 在 `HttpApi.java` 里出现 1 次，就以为它已实现；
后来发现代码里有 `if (b.acceptsFrom != null) o.putRaw(...)`，
但真正的问题是**我当时抽样看的是核心、不是带子** —— 核心的 `acceptsFrom` 本就是 null
所以不输出。**「字段没出现在我这次抽样里」和「字段没实现」是两件事。**

反向也栽过：数到 `this.rotation = rotation;` 出现 2 次，就以为锚点唯一性成立，
实际是 `UnitInfo` 和 `BuildInfo` 各有一处。

**规矩**：判「已实现」必须读那段内容。命中数只能用来排除。

### 1.2 别从**渲染后**的东西猜结构

同一个坑踩了三次：

| 场景 | 我看到的 | 实际 |
|---|---|---|
| 写补丁锚点 | `Get-Content` 显示 14 个空格 | 实际缩进不同，锚点命中 0 |
| 写补丁锚点 | 显示 20 空格 | 实际 16 空格行**是** 20 空格行的子串，`count` 返回 2 |
| 追加小节 | 以为下一个编号是「二十三」 | 文件末尾已经是「二十八」 |

**规矩**：往已有代码里插东西，一律用 `^(\s*)` 正则整行匹配、把缩进捕获下来原样带回；
追加到文件末尾前先看一眼**最后一个**小节编号。

### 1.3 清单要双向维护

- **做了要回填**：第 13 轮把三条机制写进 `ENGINE-NOTES` 就完事了，忘了把 TODO 里
  「未做」改成「已做」—— 于是两周后我自己又去核了一遍
- **过时要划掉**：`docs/reviews/` 那批笔记被当成待办收进 TODO，
  收的时候没逐条对照代码，结果 **13 条里 11 条在写下时就已过时**

**规矩**：清单与实况对不上，两个方向都要管。**收复盘内容前先跑一遍对照**，
把「已完成」标出来再收，否则清单一次比一次虚。

## 二、验证

### 2.1 验证脚本自身的错误会**伪装成被测对象的错误**

写 `drive/verify-all.py` 的过程中，脚本自己犯了三个错，每一个看起来都像功能坏了：

| 脚本的错 | 表上表现 |
|---|---|
| 没带 `Authorization` 头 | `PASS 3 / FAIL 3`，像是「五个功能同时坏了」（`/ping` 不需鉴权所以只有它过） |
| 用 beta 的 token 请求 `/v1/referee` | 「token does not belong to agent」 |
| 录像目录搜错（实际在 `Core.settings.getDataDirectory()/ai-arena-recordings/`） | 「没找到录像文件」 |

**如果没逐个去查，会得出「功能全坏了」这个完全相反的结论。**

**规矩**：验证脚本**第一件事就该确认「前提成立」** —— 服务端在不在、鉴权通不通、
文件在不在 —— 再谈功能对不对。

### 2.2 「没触发」既不是通过，也不是失败 —— 先确认瓶颈在哪一层

验「写队列每 tick 预算」时，第一次跑**没测到**：

```
(429,1429)  7618   rate limit exceeded     ← 瓶颈在令牌桶
(200)        166
```

只有 166 次真进了游戏线程。放宽限流后再跑，47 次 `1007` 如期出现。

**只看到「没触发 1007」就记成「功能可能有问题」，会得到相反结论；
直接记成「通过」，就是假绿表。**

**规矩**：一个负结果先问「是不是被别的东西挡住了」。

### 2.3 测试自身的残留会污染后续结论

`collect-place-failures.py` 第一轮崩在半路，但**已经往那些格子放了方块**；
第二轮跑时「对照组」也拿到 `1008` —— 因为格子早被占了。

这与复盘条目 24（「旧布局残留会持续制造假信号，先清场再重建」）是同一件事，
我又撞了一遍。

**规矩**：测「能不能做成某件事」之前，先确认目标位置是干净的。

### 2.4 编译通过 ≠ 能跑

八项改动攒着「只编译过」的状态跨了十几轮。等真起了服务器，
**它们一次就跑通了** —— 说明这些改动本身没问题，问题在于**没人按下启动键**。

但反过来说：**这八项在那十几轮里一直是悬着的**，任何一项都可能在第一秒崩掉。
「编译通过」只排除了语法错误。

### 2.5 这个环境里做 HTTP 验证，用 `curl.exe`

验 `/watch` 时连撞三个工具层的坑（2026-10-06），每一个都会让人以为**被测的端点坏了**：

| 坑 | 表现 |
|---|---|
| `Invoke-WebRequest` 不可用 | 直接报「Windows PowerShell 处于非交互模式。朗读和提示功能不可用」——和 HTTP 毫无关系 |
| `Invoke-RestMethod` 会返回空 | 同一个 URL、同一个 token，`$r.data` 是 `null`；换 `curl.exe` 拿到的是完整 JSON。整整两轮我在怀疑服务端 |
| **`curl` 是 `Invoke-WebRequest` 的别名** | 写了 `function Curl {...}` 并显式调 `curl.exe`，但**别名优先于函数**（优先级：别名 > 函数 > cmdlet），于是它去把 `watch` 当主机名解析，报「未能解析此远程名称」 |

**规矩**：验证接口一律写 `& curl.exe -s ...`（带 `.exe`，别起名叫 `curl`），
拿到原始字符串再 `ConvertFrom-Json` —— 别用 `Invoke-RestMethod` 的输出下结论。

这与 §2.1 是同一条：**工具的错误会伪装成被测对象的错误**，而且伪装得很像。

### 2.6 先验会盖掉实测 —— 尤其「0 度朝哪」这种有多重惯例的约定

**同一个坑在本项目里踩过两次。** `rot` 的真值是 `0=东 1=南 2=西 3=北`，
而两次都有人写成了别的：

| 谁 | 写成了 | 差在哪 |
|---|---|---|
| `ENGINE-NOTES` 初版 | `0=东 1=北 2=西 3=南` | 1 与 3 互换 |
| 干净上下文的子智能体（2026-10-06） | `0=北 1=东 2=南 3=西` | **起点错一位**（把 0 当成了北） |

**为什么会犯**：「0 度朝哪」在三种惯例里都不一样 —— 数学极坐标是**东**，屏幕/图形坐标常是**上**，
而这个引擎是**东**。没有一种「显然正确」，**只能实测**。

**真正该记的不是「它错了」，而是它错的方式**：那个子智能体**读了 `sendsTo` 里的真数据**
（报告里还写着「验证方式不是猜」），却**把自己的数据算反了**，
然后在报告里把**先验**当成**实测事实**写出来。**读过证据 ≠ 用了证据。**

**顺带**：错的模型**不会立刻崩** —— 短距离、单格的位置碰巧是对的，
长走廊批量铺才错一片（它那局 `/stalls` 峰值 18 个，大量是 `outputRefused` = 邻居方向相反）。
所以别指望「铺错了会报错」兜底：报错只在你已经铺完一片之后才来。

**文档侧的对策**：`SKILL.md` 原来只写「`rot` 取值 0–3」而**没给语义** ——
语义是**接口契约**（参数怎么传，和「HTTP 200 表示成功」同级）、**不是游戏内情**，
该写在参赛者读得到的地方。已补。

### 2.7 核对的**范围**也要核对 —— 相邻一致 ≠ 端到端可用

2026-10-06：我用 `sendsTo` 与下一格的 `acceptsFrom` 互相指认，验出「17 条带子方向 **0** 反」，
并据此报告「带子铺好了」。看观战的人当场指出：**生产了运不回，还有好几条明显没用的传送带**。

**我的核对没有骗人，但它答的不是那个问题。** 「相邻两格接得上」和「这条路有出口」是两件事：

- 一条 14 格的走廊方向**全对**，尽头却是地图上的一块巨石 —— 带子铺不上去，
  13 格带子加一台钻机的产出全堆在倒数第二格。**每一格的 `sendsTo` 看起来都对。**
- 一台压机的出料口直接朝空地：**石墨一直在产，但永远到不了核心。**

两类都只在 `/stalls` 里留一个很轻的信号（`outputRefused`），容易被当成小事放过 ——
我上一轮就把它读成了「只剩 1 条，问题不大」。

**规矩**：验一样东西之前，先问「我这个判据覆盖了目标的哪一部分」。
「方向全对」覆盖的是**局部一致性**，而目标是**端到端可用**。
**判据与目标之间的那段缺口，就是漏掉的那一层。**

**接口侧的对策**：这类「这条线没用」不该由接口直接报（那是推导，属于结论 —— 见 TODO §7.9），
但 `sendsTo` 已经把每格的下一跳给全了，**从源头追到核心是一步推导**。
已写进 `SKILL.md` §7 与 `PROMPTS.md` §三/§五。

### 2.8 转述别人的断言，等于把别人的验证当成了自己的

2026-10-06：跑第三轮对照测试时，子智能体在报告里写「**相邻的两台钻机会互相灌货**」。
**我把它当实测事实转述给了用户**，自己没查。用户当场指出：不会。

查引擎源码后确认用户对：

```java
// BuildingComp.java:869 —— acceptItem 的默认实现
public boolean acceptItem(Building source, Item item){
    return block.consumesItem(item) && items.get(item) < getMaximumAccepted(item);
}
```

**收不收取决于「这个方块消不消耗该物品」。** 钻机不消耗任何物品，所以它**根本不吃货**，
`acceptItem` 恒为 `false` —— 而全部 `acceptItem` 覆写清单（传送带、路由、核心、仓储、
工厂、炮塔…）里**没有 `Drill`**。

**根子在我自己上一轮写的文档**：我在 `SKILL.md` 里写过「`acceptsFrom` / `sendsTo` 给出每个方块
**实际**从哪几格收货、往哪几格送货（逐格的**实际结果**）」—— 这句话**对传送带成立、
对钻机不成立**（那只是"周围有建筑的格子"，是候选清单）。而 `Snapshot.java:578` 那段
**我自己写的**注释早就把这个区别说明白了。

**所以这是一条完整的错误链，起点在我**：
我的文档不准确 → 子智能体照它推理 → 我转述子智能体的结论 → 用户纠正。

**规矩**：

1. **文档里每一句「接口能做什么」，都要拿最容易误读的那类输入核一遍。**
   我写那句话时脑子里想的是传送带，可它写得像是所有方块都适用 —— 而钻机恰好是最容易被
   误读的那类（`sendsTo` 是 7~8 项的列表，看起来就像"同时在推 7 条线"）。
2. **转述第三方结论（子智能体的、工具的、别人的）时，要么标注来源，要么自己验一遍。**
   转述会把它从「某人说的」悄悄升级成「我知道的」，而那个升级是假的。
3. 这条与 §2.6「先怀疑推理」是一对：**那条讲别人会错，这条讲自己会替别人错。**

### 2.9 别用 `Add-Content` 改仓库里的文件（它写 CRLF）

2026-10-06：我用 `Add-Content CHANGELOG.md -Encoding UTF8` 追加一段，
git 立刻警告 `CRLF will be replaced by LF` —— **PowerShell 的 `Add-Content` 写的是 CRLF**，
而本仓库 `.gitattributes` 声明 `* text=auto eol=lf`。

**这个警告不能忽略**：按行匹配的锚点脚本有 101 个，
**行尾漂移会让它们静默失效**（不是报错，是"按 `^\s*xxx` 找不到那一行了"，
看上去像功能坏了，其实是行尾变了）。这也是 AGENTS.md 专门有一节讲行尾的原因。

**改仓库文件一律用 `edit` / `write` 工具**（它们写 LF）。
确要脚本手写就用：

```powershell
[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($false)))
```

改完顺手查一次：`git ls-files --eol | Select-String 'w/crlf'`（输出应为空）。
**`.ps1` 是唯一的例外**（`*.ps1 -text`，BOM 是文件内容的一部分，见 AGENTS.md 铁律 7）。

## 三、工程与流程

### 3.1 验证债要**一开始就记**

我是在**已经往无验证的范围内加了五个特性之后**才建 `TODO.md` §八 那份账的。
如果它第一轮就存在，我会更早看出：

> 在只有编译可验的地方继续加代码，是在**增加**债务，不是还债。

**规矩**：每加一个「暂时验不了」的东西，当场记一行「缺什么才能验」。

### 3.2 能复用就不要把同一件事表达两遍

- 做 SSE 时直接复用 `EventLog.Ev.toJson()`，**没有另写一份事件序列化** ——
  两份表达迟早漂移，而 SSE 与轮询说的必须是同一件事
- 条目 5「没有增量查询接口」：动手前先问「这个能力是不是已经有了」——
  答案是有，`/events?since=` 过滤出 `blockPlace`/`blockBreak`/`blockDestroy` 就是。
  再加 `/buildings?since=` 只会多一个要维护的契约

**规矩**：加端点之前先问一句「现有的东西能不能答这个问题」。

### 3.3 别实现没有收益的功能

`TODO` 里有一条「多建造单位」，前提是「多个单位能并行建」。
实际情况（由 YG 指出、并与代码核对）：**建造进度挂在具体单位上，一个单位一次只建一个方块**，
而 `/place` 默认把所有计划塞给同一个单位。

所以真正的问题不是「有没有第二个单位」，而是「计划能不能分派到不同单位」。
**照原样实现会做出一个没收益的功能。**

**规矩**：动手前把待办的**前提**验一遍，尤其是从别人笔记里继承来的前提。

## 四、本项目特有的事实（都会再错一次）

| 事实 | 表现 | 出处 |
|---|---|---|
| **地图每局重随** | 把上一局的坐标写死进脚本 → `1009 placement invalid` / `1008 blocked`，而报错完全不提「地图换了」 | `PRODUCTION.md` §一 |
| **多格方块：接口给中心、引擎按左上角** | 同一个 `rot`，2x2 与 1x1 落点差半格、输出方向也不同 | `Actor.place` 现返回 `appliedRot`/`anchorX/Y` |
| **`validPlace` 把「计划」也算占用** | 在已排计划的格上再排 1x1 → `1008`，即使那格还没有建筑 | `ENGINE-NOTES` §三十一 |
| **`rot` 越界被静默环绕** | `9→1`、`-1→3`、`4→0`，全部 `code=0`。`rot=4` 多半是调用方写成 1-based，却静默朝东 | `ENGINE-NOTES` §三十 |
| **`gamma` 没有视野** | 它站在敌方核心 5 格外，周边 31x31 的 `visible=0`。跑得快但看不见 | `ENGINE-NOTES` §二十八 |
| **建造绑定在玩家控制的单位上** | 多几个建造单位 ≠ 并行建造；`builderTooFar` 是对「被分派的那台」算的 | `API.md`「建造是单位的属性」 |
| **材料不足在下单时不拒** | 返回 `code=0`，之后由 `stuckReason: missingMaterials` 暴露 | `place-failure-stats.md` |
| **同格重复下单是 `transfer`** | 不报 1008，而是改派那个计划并返回 `previousBlock` | 同上 |
| **核心是终端，不向下游倒货** | 贴着核心的钻机会白送一份（实测一局被吃掉 198 煤） | `ENGINE-NOTES` §二十九 |
| **`router` 会被外来货物卡死** | `itemCapacity=1`，串联吞吐逐个掐死；`junction` 不会 | 同上 |

## 五、如果只记三条

1. **别拿渲染后的东西当事实。** 屏幕显示、`grep` 命中数、上次的印象 ——
   都不是代码本身。要判什么，去读那个东西。
2. **验证脚本自己也会错，而且错得像功能坏了。** 先验前提，再看结论。
3. **验证债当场记。** 一份事后才建的账，救不了已经堆上去的东西。
