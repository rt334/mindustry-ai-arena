# 产线

**目标**（原始目标，未达成）：铜 / 铅 / 硅 / 钛 / 石墨 各 **+5/s 以上**。

本文记录**实测**出来的布局与速率。所有数字都来自 `/rates`，不是推算。

---

## 一、⚠ 坐标不能写死 —— 地图每局重随

**这是本项目最贵的一个教训。**

前几版把某一局探查到的坐标写死进脚本（煤钻 (290,100)、沙钻 (289,108)、
冶炼厂 (292,102)…），下一局 `-Map veins` 重新随机后全线崩：

```
煤钻A (290,100)   1009: placement invalid        ← 那格没矿了
冶炼厂 (292,102)  1008: footprint ... blocked    ← 被别的东西占了
沙带 6格          1005: batch rejected accepted=0
```

而**错误信息完全不提「地图换了」**，只会让你以为是这一格的局部问题。

### 正确做法

坐标一律**开跑前现查**。`drive/production.py` 提供原语：

| 方法 | 作用 |
|---|---|
| `World(agent, R)` | 拉核心周边地图，自动等快照就绪 |
| `find_site(kind, size)` | 离核心最近的、size×size 全空且有该矿的点位（按矿格数优先） |
| `find_site_near_core(size)` | 贴核心的空位（冶炼厂/压机这类要直接入库的） |
| `route(a, b)` | BFS 布一条带子路径，自己绕开建筑与已计划格 |
| `lay(pts, end_rot=)` | 逐格下单并算朝向；**末格朝向必须显式给对** |
| `ready(coords)` | 轮询等建成（判据是状态，不是时长） |

`drive/bootstrap.py` 是基于它的硅线引导：从任意局面建到产出硅，零写死坐标。
在一张完全不同的图上实测通过：

```
核心 (289,104)  406 铜 / 460 铅
  冶炼厂 (285,104)     ← 自动找到贴核心的位
  煤钻A (264,111) 矿4格 → BFS 25 格带子 → 冶炼厂  ✓
  沙钻 (289,110) 矿4格  →  8 格带子 → 冶炼厂      ✓
  发电机 (284,104)     ← 贴冶炼厂，自动连电力线
  煤钻B (289,90)  矿1格 → 17 格带子 → 发电机      ✓
冶炼厂 power=1.0 eff=1.0   硅 3 ✓
```

**顺序仍不可换**：煤钻 → 燃煤发电机 → 硅冶炼厂。
（`solar-panel` 要 8 硅而硅要电，先放它就是个死循环。）

**为什么末格朝向要显式给**：`route()` 只知道怎么走到目标旁边，
不知道料该往哪个方向进。末端格子如果朝向错了，整条带子看着通、实际不送料。

## 二、实测速率

| 资源 | 速率 | 来源 |
|---|---|---|
| 铜 | **+0.32 ~ +0.40 /s** | 1 台机械钻 |
| 硅 | **+0.28 ~ +0.36 /s** | 1 台冶炼厂 |
| 煤 | +0.32 /s（净） | 2 台钻机，大部分被消耗 |
| 铅 / 钛 / 石墨 | 0 | 未建 |

**单台机械钻 ≈ 0.35 /s。** 所以 +5/s 需要**每种约 14 台钻机**——这是个大工程，
得靠「一条收集带穿过一排钻机」的方式规模化，不能一台一台铺线。

## 三、踩过的坑（都会再犯，记下来）

**电力死循环**：`solar-panel` 要 8 硅，而硅要电。第一版直接卡死。
破局靠 `combustion-generator`（1×1，`{copper:25, lead:15}`，**不含硅**）烧煤供电。
开工顺序必须是：煤钻 → 燃煤发电机 → 硅冶炼厂，不能先想太阳能。

**`stuckReason` 是最好的诊断入口**。这轮两次靠它一眼定位：
```
solar-panel stuck=311 reason=missingMaterials: solar-panel needs 8 silicon, core has 0
```
它直接说出了缺哪样、缺多少、核心有多少。别先去翻 `/stalls` 或 `/drill`。

**多格方块的坐标是中心**。`(301,99)` 的 2×2 钻机占 `x[301,302] y[99,100]`，
所以 `(300,101)` 与它只是**对角**相邻 —— 而输送必须四邻相邻。
漏这一格，整条煤带一根煤都送不到，发电机 `power=0.0`。

**`place_path` 的 `accepted` 可能小于 `requested`**，被拒的格子不会告诉你为什么。
这轮煤带 `requested=7 accepted=6`，被拒的 `(289,100)` 上**已经有铜带**——
于是整条煤链断在第一格，压机 `eff=0` 却看不出原因。
**每次 `place_path` 之后都要看 `accepted` 是不是等于 `requested`**。

**煤是当前瓶颈**。2 台钻机毛产 ~0.7/s，消费者有核心 + 冶炼厂 + 发电机 + 压机。
核心会**无限吸煤**（钻机与它相邻就白送），这轮被它吃掉 198 煤。

## 四、产率模型（已从引擎源码确认，并实测复核）

**公式**（`Mindustry-src/core/src/mindustry/world/blocks/production/Drill.java`）：

```java
// Drill.java:303 —— 注意 dominantItems 是直接乘数
lastDrillSpeed = (speed * dominantItems * warmup) / delay;
// Drill.java:171
delay = (drillTime + hardnessDrillMultiplier * item.hardness) / drillMultiplier;
// hardnessDrillMultiplier = 50
// Drill.java:149 放置预览里直接印了这个式子
text = 60f / getDrillTime(item) * returnCount   // 个/秒
```

即 **每秒产率 = 60 × 矿格数 ÷ (drillTime + 50 × 硬度) × warmup**。

`dominantItems` 是钻机脚印内的主矿格数，**上限 size×size**。所以产率正比于
脚下了几格矿 —— 不是「有矿就行」。上一版用「前后产率差」测这个，
结果被 `Actor.place` 的扣料污染（铜产率一度测成 −0.400/s），白跑一轮。

### 各种钻机

| 钻机 | 占地 | tier | drillTime | 成本 |
|---|---|---|---|---|
| mechanical-drill | 2×2 | 2 | **600** | copper 12 |
| pneumatic-drill | 2×2 | 3 | **400** | copper 18 + graphite 10 |
| laser-drill | 3×3 | 4 | **280** | copper 35 + graphite 30 + silicon 30 + titanium 20 |
| blast-drill | 4×4 | 5 | **280** | copper 65 + silicon 60 + titanium 50 + thorium 75 |

`tier` 是能挖的最高硬度。**mechanical 挖不了钛（tier2 < 硬度3）；
pneumatic 挖不了钍（tier3 < 硬度4）。**

### 实测复核

在 4 格煤矿上放一台机械钻（无输出，自然填满）：

```
矿格=4  硬度=2  warmup≈0.93
引擎公式   60 × 4 / (600 + 50×2) = 0.343 /s
接口字段   itemsPerSecond        = 0.32
比值 0.933  ← 正好是当时的 warmup
```

### ⚠ `lastDrillSpeed` 是**每 tick**，不是每秒

引擎 UI 要 `lastDrillSpeed * 60 * timeScale` 才是每秒（`Drill.java:118`）。
它只有两位小数，`0.01` 可能对应真实 `0.0062` —— 我照着「个/秒」写注释，
结果看到 `0.01` 以为 100 秒才出一个矿，和实测的 0.35/s 对不上，白查一轮。

**已修**：`/drill` 现在同时给出 `itemsPerSecond`（在 Java 里先 ×60 再序列化，
绕开两位小数的舍入）与 `dominantItems`。**读 `itemsPerSecond`。**

## 五、可达性：用正确的模型重算

已知事实：

- 5 台机械钻里，4 台是 **矿格=4**，`lastDrillSpeed` 报 **0.01**
- 新放的 (274,106) 是 **矿格=2**，报 **0.0**

`lastDrillSpeed` 只有两位小数，0.01 对应真实约 0.0059/tick（≈0.35/s，与核心
铜产率实测吻合）。`0.0` 意味着 <0.005 —— 所以**矿格少的钻机确实更慢**。

但这一条**不能算定论**，因为：

- 用「前后产率差」测的那一轮被污染了：`Actor.place` 会从核心扣料，
  测量窗口里混进了建造消耗，铜产率一度测成 **−0.400/s**
- 静置重测仍然抖：同一次 4 个采样是 −0.10 / −0.08 / −0.05 / **+0.53**
- `/rates` 的窗口里有锯齿，单次采样不可信

**要测准必须**：先让队列清零并静置，再用长窗口多次采样取中位数，
且期间不下任何建造单。下次重测时按这个来做。

**这个问题的答案直接改变 §四 的表**：若产率正比于矿格数，则「可放钻机位」
这个口径就过于乐观，真正该统计的是**总矿格数 / 每台占用的矿格数**。

## 六、规模化实测

用 `drive/scale-copper.py`（基于 `production.py` 的自动选点 + BFS 布线）铺铜。

### 第一轮：6 台钻机，每台 4 格铜

```
模型预测  6 × 4 格 × 60/650 = 2.22 /s
实测最高                    2.04 /s   → 兑现 92%
```

**模型在规模化下成立。** 核心铜速率从 **+0.35/s 提到 +2.04/s**。

个别钻机的失败与布线长度无关，都是布局冲突：
```
钻机4 (295,93)   1008   footprint blocked
钻机7 (321,104)  布不出线
```

### 第二轮：全败 —— 带子拥堵

再铺 12 台时，7 个候选**全部「布不出线」**：

```
钻机0 (278,126) 布不出线
钻机1 (279,128) 布不出线
... 7 个全失败
```

原因不是找不到路，是**路被自己堵死了**。第一轮的 6 条独立带子加起来 211 格
（40+46+9+15+50+51），在核心周边织成一张网，把剩下的铜点围在里面。
`route()` 会绕开已有建筑，但绕不开"所有通路都被占满"。

**这是规模化的真正障碍。** 「每台钻机拉一条专线回核心」在十几台时还能跑，
再多就不行 —— 线本身变成了墙。

### 下一版要做的是「收集干线」

不是给每台钻机布线，而是：

1. 先沿铜脉拉**一条**干线（横穿整个矿区）
2. 钻机沿干线排列，2×2 钻机紧贴干线放置 —— 钻机向**所有**四邻输出，
   所以只要有一格挨着干线，料就自动上线，**不需要额外支线**
3. 干线只在末端接一条回核心

这样 N 台钻机只占 1 条回程线，而不是 N 条。`World.route()` 仍然有用，
但只用一次。

**选点约束也随之变化**：不再是「哪格空」，而是「哪些 2×2 位置紧贴干线
且盖住尽可能多的矿格」。这正好回到 `coverage-ceiling.py` 里的覆盖优化 ——
区别是加了「必须贴干线」这条约束。

| 资源 | 速率 | 说明 |
|---|---|---|
| 铜 | **+2.04 /s**（实测） | 12 台钻机，`/drill` 汇总 2.86 /s |

## 七、干线实测

`drive/trunk.py`：沿矿脉拉一条直干线，钻机紧贴两侧排列（钻机向所有四邻输出，
贴一格就自动上线，**不需要支线**），末端接一条回程。

干净图上第一次就选中：干线 `y=124 x[271,309]`（39 格），5 台钻机，
回程 34 格。

### 模型被精确确认

```
(303,125) 矿格=4  itemsPerSecond=0.37    60×4/650 = 0.369  ✓
(305,122) 矿格=4  itemsPerSecond=0.37                       ✓
(307,125) 矿格=4  itemsPerSecond=0.37                       ✓
(305,125) 矿格=4  itemsPerSecond=0.37                       ✓
(307,122) 矿格=2  itemsPerSecond=0.18    60×2/650 = 0.185  ✓

/drill 汇总 copper = 1.66 /s             18 格 × 60/650 = 1.66  ✓
```

**逐台、以及汇总，都和公式对上了。** 产率公式现在可以当准绳用。

### 但料到不了核心：干线断了

下单结果：**干线+回程 58/72 格**，14 格被 `1008` 拒：

```
(272,124) 1008   (273,124) 1008   (274,124) 1008   ...
```

**而这 14 格 `free()` 明明报的是空。** 核心铜因此卡在 382 不动 ——
钻机在产出，只是送不出来。

最可能的原因是**地图快照有滞后**：`free()` 读的是 `/map` 的缓存快照，
而引擎已经看到实地有固体地形（墙）。于是判据说「空」、引擎说「挡」。
这与 `DEVELOPING.md` 里记的那条坑（「读端点读缓存」）是同一类。

**下一代要加的自检**：`lay()` 之后必须核对 `accepted == requested`，
**不等就重新布线再试**，而不是把断线当成建好了。这次就是先看到
「58/72」却没当回事，直到测出核心不涨才发现。

### ⚠ `/rates` 开局会给出假值

同一轮里 `/rates?window=30` 报过 **+13.63 /s** 甚至 **+20.56 /s** ——
全都是假的：窗口跨了核心初始化的那一跳（采样里出现 `start=0`）。

**开局头一分钟不要信 `/rates`。** 要看真实产率，用 `/drill` 的
`itemsPerSecond` 汇总 —— 它是逐台的瞬时值，没有窗口污染。
