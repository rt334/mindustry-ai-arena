### 7.1 接口暴露缺失

| # | 项 | 性质 | 优先级 |
|---|---|---|---|
| 1 | **conveyor 的收货规则仍未暴露成字段**。四份文档共同指认的头号时间黑洞：`/buildings` 该给每个 conveyor 直接回 `acceptsFrom`。规则**已用实机实验定论**（背面 `minitem >= 0.4` 是主收货口、两侧 `> 0.7` 门槛更高、正面即下游绝对拒收），但接口侧只有 `sendsTo`，`acceptsFrom` 与四元组真值表都没实现。**动手前先核对 `sendsTo` 的实现范围**，避免重复劳动。 | 待做 | **P0** |
| 2 | **钻机「实际在往哪几格推货」没有任何接口能查**。矿机输出**不受 `rotation` 控制**，只要邻格能收就推——所以「把沙钻放在煤干道旁边」必然灌沙顶死整条线，这是增补作者自认的最大时间黑洞。同一诉求包含：`/place` 返回体带「实际生效的 rot + 输出格坐标」、解释 footprint 锚点为何让同 `rot=2` 落点不同（`(68,101)→(67,102)` 西南 vs `(61,108)→(60,108)` 正西）。 | 待做 | **P0** |
| 3 | **`/queue` 只给数量不给坐标与进度**。只看到 `plans: 27 / 50 / 95`，导致建造加速器必须自维护 `pending.json`，而该清单因丢单长期与服务端不一致。建议返 `[{x, y, block, progress}]`。 | 待做 | P1 |
| 4 | **`/units` 缺「当前在建哪个方块」**。建议加 `buildingAt: {x, y, progress}`，否则建造加速只能按清单盲撞。B2/B3 落地后，warp 加速器与 `op=order` 两种 workaround 都能退役。 | 待做 | P1 |
| 5 | **没有增量查询接口**。每步改动都要重拉全量 `/buildings`（后期 250+ 条）对比。 | 待做 | P2 |
| 6 | **`/map` 的单次窗口上限未暴露，400 响应体也不说明原因**。`w=84&h=84` 直接 `HTTP 400` 且无任何文字，现场靠试错得出 32 可用，`localmap.py` / `survey2.py` 里的 `STEP=32` 是硬编码。 | 待做 | P2 |
| 7 | **`/place` 的 `config` 参数无效，且 sorter 的 `rotation` 回读恒为 0**。`place?config=coal` 建出来 `config` 是 `None`，必须后置调 `/config`；正是这一步让「石墨倒回煤道 → 熔炉拒收 → 整条煤道死锁 → 硅长期 0」卡了很久。 | 待做 | P1 |
| 8 | **`/stalls` / `/diag` 不区分「上游来货不足」与「下游拒收」两种停机**。核心铜满 13000 会让整条上游线反向堵塞、所有铜钻机 `eff=0.0` 且满仓，但接口读起来像是「没矿可挖」。可靠判据是 `eff == 0.0` 且 `items` 达容量上限。 | 待做 | P1 |
| 9 | **视野半径未暴露，且 `place` 出视野返回 HTTP 403 而非 JSON**。正文是 `HTTP Error 403: Forbidden`，**只看 JSON body 的错误处理会直接误判**。建议在 `/content` 或 `/state` 暴露视野半径（实测约 61 格），403 响应体写明原因。附带结构性事实：视野由己方建筑提供，长距离扩张必须分段推进，否则鸡生蛋。 | 待做 | P2 |
| 10 | **队列停滞的处理手段与坐标语义都没文档化**。`POST /control?op=order&unit=<id>&x=&y=` 实测把 `plans` 从 56 一次降到 1 并真的建成了沿线方块（单位卡在建造状态机里，移动命令重置了状态）；而 `break` 一个**空格**想取消排队计划是**无效的**，反而会追加拆除计划（47 → 56）。建议 `/queue` 能自行判定「停滞」并把这条列为可操作项；`op=order` 的坐标是**格坐标不是像素**，需写进接口文档。 | 待做 | P1 |

### 7.5 教训（写给后来人）

| # | 教训 |
|---|---|
| 20 | **调试前先确认没有别的进程在操控同一支队**。`ai-client.py --agent alpha`（PID 44384）在后台往同一批格子插带子，导致「建造计划成功但不生效」，在此之前所有改动都不可归因。查 `Win32_Process` 是第一步。 |
| 21 | **「排队成功」不等于「生效」；判据必须是状态，不是时长**。`{"message": "queued ... pending plans=1"}` 之后方块可能永不出现。纪律是全部走 `poll_until(pred, timeout)`，代码里不出现裸 `sleep(N)`。 |
| 22 | **混料是「互相顶死」不是「减速」**。一条 conveyor 一次只持有一个物品（`capacity=3` 是长度计数），两种资源共用一条线会互相卡住。典型链条：沙灌进煤干道 → 煤上不去 → 上游煤矿机满仓 `eff=0.0` → 压机没煤 → 没石墨就建不了 pneumatic-drill → 挖不了钛。**根因不是「铺错了」，而是「把它放在别人的物流线旁边」这个动作错了。** |
| 23 | **静态分析在方向语义上不可靠，必须单侧隔离实测**。用「两侧都铺带子看哪边先来货」会把「侧向也能收」误读成「只有一边收」；正确装置是**一次只开一个方位**，或用「矿机 + 8 邻格全铺同 rot 带子」让被测格只暴露收货规则。 |
| 24 | **旧布局残留会持续制造假信号，先清场再重建**。错向带子、僵尸计划（卡在 build 状态占死 2x2 footprint、堵掉钻机唯一出口、损失约 0.4/s）都是「一次只改 1~2 格 + 立刻复测」之后才定位的；打补丁不如清干净。 |
| 25 | **排查产出必须及时转化成接口需求**。同等人力，7 轮「建造为主 + 遇到坑就绕过」的产出是 283 段带 / 26 台钻机 / 可运行产线；29 轮「排查为主 + 每个坑写成笔记」的产出是 25 节笔记和一堆诊断脚本，**游戏里没多出一台钻机**。坑应尽早变成「接口该怎么改」，而不是留给自己反复踩。 |

### 7.6 复盘给出的三件优先事

1. **把 conveyor 收货规则与钻机实际推货格暴露进接口**（条目 1+2）——四份文档独立指认的头号时间黑洞，且规则已用实机实验定论，只剩落地，ROI 最高。
2. **改掉 `ENGINE-NOTES.md` 里写反的 `rot` 编码**（条目 13）——一个字符的修正，能阻止后续所有朝向推理继续错位 180°。
3. **补齐失败语义**：403 语义 / 视野半径 / `/queue` 停滞判定与 `op=order` 解法（条目 9+10）——现在这些把可恢复的失败伪装成不可恢复，直接导致 AI 盲重试或误拆方块。
